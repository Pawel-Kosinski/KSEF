1. Cel systemu i architektura

Wirtualny CFO to MVP platformy B2B dla polskich MŚP. System pobiera faktury ze schematu FA(3) (Krajowy System e-Faktur) przez API KSeF 2.0, parsuje je, kategoryzuje pozycje towarowe/usługowe za pomocą lokalnego modelu językowego (Ollama), zapisuje wyniki w PostgreSQL z izolacją danych per firma (tenant), a następnie udostępnia zagregowane statystyki i listę faktur przez REST API oraz dashboard Next.js.

Klucowa zasada biznesowa (od v2.0): faktury są rozróżniane jako kosztowe (invoice_role=cost, KSeF Subject2 — firma jest nabywcą) lub sprzedaż (invoice_role=sales, KSeF Subject1 — firma jest sprzedawcą). Dashboard i statystyki filtrują dane według tej roli — faktury sprzedaży nie są traktowane jako wydatki.

4.3. Row-Level Security (RLS)

Izolacja multi-tenant jest wymuszana na poziomie PostgreSQL, nie tylko w kodzie aplikacji. Mechanizm opiera się na zmiennej sesyjnej app.current_tenant. 

-- Ustawienie kontekstu (app/database/session.py → set_tenant_context):
SELECT set_config('app.current_tenant', '<uuid-tenanta>', true);
-- trzeci argument true = SET LOCAL (reset po COMMIT/ROLLBACK)

-- Polityka RLS (migracja 001, tabele invoices, invoice_lines, tenant_categories):
CREATE POLICY tenant_isolation_policy ON <table>
FOR ALL
USING (tenant_id = NULLIF(current_setting('app.current_tenant', true), '')::UUID)
WITH CHECK (tenant_id = NULLIF(current_setting('app.current_tenant', true), '')::UUID);

Migracja 003 (FORCE RLS): Właściciel tabeli (użytkownik aplikacji) nie może omijać RLS. Bez tego PostgreSQL domyślnie pozwala ownerowi widzieć wszystkie wiersze.

Dwutorowe zabezpieczenie w analityce: StatisticsService dodatkowo filtruje WHERE InvoiceLine.tenant_id = self._tenant_id — jawny filtr w SQL jako defense-in-depth.

5. Uwierzytelnianie i multi-tenancy

5.1. Model JWT (tryb deweloperski)

W MVP nie ma pełnego logowania użytkownika. Token JWT jest generowany skryptem scripts/create_dev_token.py i zawiera: 

{
  "sub": "dev-user",
  "tenant_id": "<UUID tenanta z bazy>",
  "exp": <timestamp UTC + 24h>
}

5.2. Przepływ autoryzacji w żądaniu HTTP

  1. Klient wysyła nagłówek Authorization: Bearer <token>
  2. get_current_tenant (dependencies/tenant.py) dekoduje JWT kluczem JWT_SECRET_KEY
  3. Wyciąga tenant_id → tworzy obiekt TenantContext
  4. get_rls_session otwiera transakcję async, wywołuje set_tenant_context, yielduje sesję SQLAlchemy
  5. Po zakończeniu handlera: COMMIT (lub ROLLBACK przy błędzie)

5.3. Middleware TenantRLSMiddleware

Plik middleware/tenant_rls.py — opcjonalnie parsuje JWT i ustawia request.state.tenant_id. Główna ścieżka RLS to dependency injection (get_rls_session), nie middleware. Middleware jest pomocniczy i nie blokuje żądań przy nieprawidłowym tokenie.

9. Moduł kategoryzacji AI (Ollama)

9.1. Klasa ProductCategorizer

Plik: app/services/ai/categorizer.py

Przepływ classify_product_name(product_name, allowed_categories)

  1. validate_allowed_categories() — lista niepusta, bez duplikatów
  2. _assert_product_name_isolation(product_name) — walidacja P_7:
    • niepuste, max 512 znaków
    • brak NIP (regex 10 cyfr)
    • brak kwot pieniężnych (wzorzec z 2 miejscami po przecinku lub separatorem tysięcy)
    • brak adresu e-mail
  3. build_category_schema(categories) — dynamiczny Pydantic z Literal[kat1, kat2, ...]
  4. build_category_json_schema() — JSON Schema dla parametru format Ollama
  5. build_system_prompt(categories) — prompt systemowy z listą dozwolonych kategorii
  6. Wywołanie AsyncClient.chat():
    • model: OLLAMA_MODEL (domyślnie qwen2.5:7b)
    • temperature: 0.0
    • num_predict: 128
    • format: JSON Schema (structured output)
  7. _sanitize_model_payload() — czyszczenie artefaktów JSON z odpowiedzi SLM
  8. schema_cls.model_validate(payload) — walidacja Pydantic

10.2. Sekwencja uwierzytelniania tokenem KSeF

POST /auth/challenge
Pobranie jednorazowego challenge i znacznika czasu
→ challenge, timestampMs
GET /security/public-key-certificates
Pobranie certyfikatów publicznych MF do szyfrowania tokena
→ wybór certyfikatu (public_key_id)
RSA-OAEP SHA-256
Szyfrowanie ciągu: ksef_token + "|" + timestampMs
→ encrypted_token (base64), public_key_id
POST /auth/ksef-token
Body: challenge, contextIdentifier: {type:"Nip", value: NIP}, encrypted_token, public_key_id
→ reference_number, authentication_token
POLL GET /auth/{referenceNumber}
Nagłówek: Authorization: Bearer <authentication_token>
→ kod 100 = w toku  |  kod 200 = sukces  |  max 60 prób × 1 s
POST /auth/token/redeem
Nagłówek: Authorization: Bearer <authentication_token> (jednorazowo)
→ access_token, refresh_token (+ valid_until)

Uwaga implementacyjna: NIP kontekstu biznesowego idzie do contextIdentifier w /auth/ksef-token, nie do /auth/challenge.

Test auth: scripts/test_ksef_auth.py — wymaga KSEF_TOKEN w .env (NIP z rekordu tenanta w bazie).
